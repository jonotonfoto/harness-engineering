J01Определение

Что это такое

Всё, что вокруг модели, проектируется так же тщательно, как код

Harness (обвязка) — это программная среда вокруг языковой модели: цикл, который вызывает модель, инструменты и их описания, файловая система и песочница, управление контекстом и памятью, проверки, хуки, права и логи. Раньше это называли scaffolding, «строительные леса».

Harness engineering — практика относиться к этой среде как к настоящему инженерному артефакту. Её проектируют, тестируют и ужесточают каждый раз, когда агент ошибается. Формула Хашимото: увидел ошибку агента — потрать время, чтобы встроить в среду решение, после которого эта ошибка больше не повторится.

Важное отличие от обычной инженерии: обёрнутый компонент недетерминирован. Модель может выдумать действие или объявить работу законченной, когда она не закончена. Обвязка спроектирована так, чтобы ловить это и спокойно восстанавливаться.

horse harnessУпряжь

Исходное значение. Сила лошади полезна, только когда её направляет сбруя. Модель — лошадь, обвязка — упряжь и вожжи.

wiring harnessЖгут проводов

В машиностроении — собранный пучок проводов с разъёмами, который соединяет блоки. Отсюда схема этой страницы.

test harnessТестовая обвязка

В программировании — окружение, которое запускает код и проверяет результат. Проверки остаются ядром и агентной обвязки.

Если ты не модель, ты обвязка.

J04Анатомия

Из чего состоит обвязка

Девять жил одного жгута

Слева то, что направляет модель до действия. Справа то, чем она действует и что проверяет результат. Разъём в центре — модель. Ни одна жила не обязательна сама по себе: каждая закрывает конкретный провал, замеченный в работе.

Цикл агента. Ядро любой обвязки — простой цикл: вызвать модель, выполнить запрошенные инструменты, вернуть результат, повторять до ответа. В Managed Agents Anthropic вся обвязка — это именно этот цикл без состояния.

Хуки и middleware. Детерминированный код, который срабатывает на событиях: сжатие контекста, продолжение работы, запуск линтера после правки, запрет опасной команды до её выполнения.

Модель и обвязка срослись. По оценке LangChain, Claude Code и Codex дообучают вместе с их обвязкой. Полезный приём сначала появляется в обвязке, потом модель учат им пользоваться.

J05Управление

Модель Thoughtworks / martinfowler.com

Направляющие до действия, датчики после

Böckeler описывает обвязку языком теории управления. Направляющие (guides, feedforward) предугадывают поведение агента и задают курс до того, как он начнёт: повышают шанс попасть с первой попытки. Датчики (sensors, feedback) смотрят на результат и дают агенту исправиться. Особенно сильны датчики, чьи сообщения написаны для модели: например, линтер, который сразу пишет, как исправить нарушение.

Вторая ось — вычислительные проверки (детерминированные, быстрые, дешёвые) против инференциальных (оценивает другая модель: медленнее, дороже, недетерминированно, зато видит смысл).

Три объекта регулирования

Сопровождаемость кода, соответствие архитектуре и поведение системы. Для поведения направляющая — спецификация, датчик — тесты плюс ручная проверка человеком.

Держи качество слева

Дешёвые датчики запускаются сразу при генерации, дорогие (архитектурное ревью, мутационные тесты) — в пайплайне после интеграции. Stripe подчёркивает, как важен для их Minions принцип «shift feedback left».

Harnessability

Не любой код одинаково легко обвязать. Строгие типы, явные границы модулей и фреймворки, скрывающие детали, делают кодовую базу удобнее для агента. Закон Эшби: регулятор должен быть не беднее регулируемой системы, поэтому стандартные топологии и шаблоны обвязки сужают разнообразие.

J06Anthropic · ноябрь 2025

Effective harnesses for long-running agents

Инженеры, работающие сменами без памяти

Главная трудность долгих задач: агент работает отдельными сессиями, и каждая новая начинается с чистого листа. Anthropic сравнивает это с проектом, где инженеры работают посменно, и каждый новый ничего не помнит о прошлой смене.

Даже Opus 4.5 на Claude Agent SDK со сжатием контекста не собирал приложение уровня продакшена по фразе «сделай клон claude.ai». Провалы были двух видов: агент пытался сделать всё за один заход и обрывался посреди фичи, а позже другой экземпляр видел прогресс и объявлял проект готовым.

Решение — два промпта. Агент-инициализатор в первой сессии готовит среду. Агент-кодер в каждой следующей делает одну фичу и оставляет чистое состояние, пригодное для слияния в main. Системный промпт, инструменты и обвязка у них одинаковые, различается только первое сообщение.

артефактinit.sh

Поднимает dev-сервер, после чего агент проходит базовый сквозной тест. Агенту не нужно каждый раз выяснять, как запускать проект.

артефактclaude-progress.txt

Журнал того, что сделали прошлые сессии. Вместе с историей git позволяет быстро понять состояние работы.

артефактgit

Первый коммит от инициализатора, затем коммит с внятным сообщением после каждой фичи. Плохую правку можно откатить.

Ритуал начала каждой сессии

  1. Выполнить pwd: понять, в какой папке работаешь и что можно править.
  2. Прочитать git log и файл прогресса.
  3. Открыть список фич и выбрать самую приоритетную из невыполненных.
  4. Запустить init.sh и пройти базовый сценарий в браузере.
  5. Если что-то сломано, сначала чинить, а потом браться за новое.
  6. В конце: коммит и запись в файл прогресса.

Тестировать как человек

Агент охотно отмечал фичу готовой после юнит-тестов или curl, не проверив её сквозь интерфейс. Когда ему дали автоматизацию браузера (Puppeteer MCP) и велели проверять как пользователь, качество резко выросло.

Остались слепые зоны: например, нативные alert-окна браузера через Puppeteer не видны, и фичи на них выходили более багованными.

J07Anthropic · март 2026

Harness design for long-running application development

Один строит, другой придирается

Следующий шаг Anthropic Labs вдохновлён генеративно-состязательными сетями (GAN). Две проблемы оставались после первой обвязки. Первая — потеря связности при заполнении окна и «тревога контекста»: модель сворачивает работу, думая, что лимит близко. Вторая — самооценка: агент уверенно хвалит свою работу, даже когда она посредственна. Настроить отдельного скептичного оценщика оказалось гораздо проще, чем научить генератора критиковать себя.

агент 1Планировщик

Разворачивает промпт в 1–4 предложения в полную продуктовую спецификацию. Амбициозно по объёму, но без деталей реализации: ошибка в спеке каскадом уходит вниз.

агент 2Генератор

Строит приложение по одной фиче за спринт (React, Vite, FastAPI, SQLite/PostgreSQL), сам проверяет себя и сдаёт работу в QA.

агент 3Оценщик

Через Playwright MCP прокликивает живое приложение как пользователь, проверяет UI, API и БД. У каждого критерия жёсткий порог: ниже порога — спринт провален.

Контракт спринта

Перед каждым спринтом генератор и оценщик договариваются, что значит «готово»: что будет построено и как это проверить. В спринте 3 одной игры было 27 критериев только для редактора уровней. Общение шло через файлы: один агент пишет, другой читает и отвечает.

Критерии для дизайна

Качество дизайна, оригинальность, ремесло, функциональность. Первые два весили больше: по ремеслу и функциональности Claude и так хорош, а по оригинальности выдаёт безопасные шаблоны. Критерии прямо штрафовали узнаваемый «AI slop».

Scaling Managed Agents with stable interfaces

Мозг отдельно, руки отдельно, память отдельно

−90%+время до первого токена в хвосте (p95)
1интерфейс для любых рук: имя и вход внутрь, строка наружу

Обвязка кодирует предположения, которые устаревают с каждой моделью. Поэтому Anthropic делает стабильными интерфейсы вокруг неё, а саму логику обвязки меняет от поколения к поколению.

Цель — читаемость для агента

Всё, чего агент не видит в репозитории, для него не существует. Решения из чатов и голов переносятся в репозиторий как версионируемые документы.

Приложение поднимается в каждом git worktree отдельно. Chrome DevTools Protocol подключён к рантайму, есть скиллы для DOM, скриншотов и навигации, локальные логи и метрики.

Архитектура закреплена кодом

Строгие слои внутри домена с допустимыми направлениями зависимостей. Нарушения ловят свои линтеры и структурные тесты, и их сообщения подсказывают агенту, как исправить.

Комментарии ревью, рефакторинги и баги от пользователей становятся документацией. Если документации не хватает, правило переносится в код.

Пропускная способность меняет слияние

Минимум блокирующих ворот, короткоживущие PR, флаки лечатся повторным прогоном. Исправления дешёвые, ожидание дорогое. В медленной команде так делать безответственно.

Энтропия и сборка мусора

Codex повторяет паттерны, которые уже есть в репозитории, включая плохие. Сначала команда каждую пятницу, то есть 20% недели, вручную вычищала «AI slop». Это не масштабировалось.

Новая роль инженера

Люди остаются в контуре, но на другом уровне: расставляют приоритеты, превращают отзывы пользователей в критерии приёмки, проверяют результат. Когда агент буксует, это сигнал: чего не хватает — инструмента, ограждения или документа? Недостающее добавляется в репозиторий, и пишет его тоже Codex.

Приложение поднимается отдельно в каждом git worktree. Протокол Chrome DevTools подключён к среде агента, для DOM-снимков, скриншотов и навигации написаны скиллы. Цикл проверки:

Наблюдаемость на каждую задачу

Логи, метрики и трейсы доступны агенту через локальный стек, который живёт, только пока жив worktree, и удаляется после задачи. Логи агент запрашивает на LogQL, метрики на PromQL.

С таким контекстом выполнимыми становятся промпты вида «запуск сервиса должен укладываться в 800 мс» или «ни один интервал в четырёх критичных сценариях не дольше двух секунд».

Один запуск Codex регулярно работает над задачей больше шести часов, часто пока люди спят.

Скучные технологии выигрывают

Предпочтение отдаётся зависимостям, которые можно целиком понять внутри репозитория. Технологии, которые называют скучными, агенту проще моделировать: они компонуются, у них стабильный API и их много в обучающих данных. Иногда дешевле попросить агента заново написать нужный кусок, чем обходить неочевидное поведение публичной библиотеки. Вместо пакета в духе p-limit команда сделала свой map-with-concurrency: он встроен в их OpenTelemetry, покрыт тестами на 100% и ведёт себя ровно так, как нужно их рантайму.

Вне бизнес-домена. Всё остальное запрещено и проверяется механически.

Такую архитектуру обычно откладывают, пока в компании не наберутся сотни инженеров. С агентами она нужна с самого начала: ограничения дают скорость без дрейфа. Правило звучит как «держи инварианты, а не реализацию»: например, данные обязательно разбираются на границе, но библиотека не предписана (модели сами тяготеют к Zod). Свои линтеры следят за структурированным логированием, именованием схем и типов, размером файлов и требованиями к надёжности. Человеческий стиль кода не обязателен: достаточно, чтобы код был корректным, поддерживаемым и читаемым для следующих запусков агента.

Один промпт, полный цикл фичи

  1. Проверить текущее состояние кодовой базы.
  2. Воспроизвести зафиксированную ошибку.
  3. Записать видео, где ошибка видна.
  4. Реализовать исправление.
  5. Проверить исправление, запустив приложение.
  6. Записать второе видео, где ошибки больше нет.
  7. Открыть pull request.
  8. Ответить на замечания агентов и людей.
  9. Найти и починить падения сборки.
  10. Позвать человека, только когда нужно суждение.
  11. Влить изменения.

PR доводится до конца циклом Ральфа Виггума: агент просит ревью у других агентов локально и в облаке, отвечает на замечания и повторяет, пока все рецензенты не довольны. Люди могут смотреть PR, но не обязаны.

Два золотых принципа

Общие пакеты утилит вместо самописных хелперов, чтобы инварианты жили в одном месте.

Никакого прощупывания данных наугад: проверять границы или работать через типизированные SDK, чтобы агент не строил логику на догадках о структуре.

Агенты гораздо эффективнее, когда попадают с первого раза. Надёжнее всего этого добиться, если дать им быстрые инструменты, которые автоматически говорят, что агент ошибся. Две формы:

Неявный промпт. Агент запускает не те команды или ищет не те API — в AGENTS.md добавляется строка. В AGENTS.md терминала Ghostty каждая строка появилась из конкретного плохого поведения, и это почти полностью их устранило.

Настоящие инструменты. Скрипты для скриншотов, отфильтрованных тестов и так далее, плюс строка в AGENTS.md, чтобы агент знал о них.

J15Сбои

Что ломается и чем лечится

Восемь типовых отказов

Всё за один заход

Агент пытается собрать приложение целиком, кончается контекст, фича брошена на середине. Лечение: список фич и одна фича за сессию.

Преждевременная победа

Новый экземпляр видит прогресс и объявляет проект готовым. Лечение: JSON-список со статусом каждой фичи.

Тревога контекста

Модель сворачивает работу, думая, что окно почти заполнено. Лечение: сброс контекста с передачей состояния. У Opus 4.5+ проявляется слабо.

Самовосхваление

Агент хвалит свою посредственную работу, оценщик уговаривает себя, что баг несерьёзный. Лечение: отдельный оценщик, калибровка на примерах, жёсткие пороги.

Петля обречённости

Агент ходит по кругу с мелкими вариациями одного неработающего подхода. Лечение: middleware, которое считает повторы и вмешивается.

Готово без проверки

Юнит-тесты прошли, а в интерфейсе фича не работает. Лечение: браузерная автоматизация и сквозные проверки.

Дрейф и AI slop

Код постепенно копирует худшие паттерны репозитория. Лечение: архитектурные линтеры и регулярная сборка мусора.

Гниение обвязки

AGENTS.md разрастается, правила противоречат друг другу и устаревают. Лечение: короткая карта, проверка свежести, удаление ненесущих частей.

Старое название того же самого. Встречается в докладе британского правительства к AI Safety Summit, октябрь 2023.
AGENTS.md
Открытый формат файла инструкций для агентов в корне репозитория. Подгружается в контекст при старте.
Skill · навык
Папка с инструкциями и скриптами, которую агент подгружает только когда задача её касается.
Hook · хук
Детерминированный код на событии агента. PreToolUse может запретить действие до выполнения.
MCP
Model Context Protocol, стандартный способ подключать к агенту инструменты и источники данных.
Compaction · сжатие
Пересказ ранней части диалога на месте, чтобы тот же агент продолжал работу.
Context reset · сброс
Новый агент с чистым окном плюс артефакт передачи состояния. Лечит тревогу контекста.
Context anxiety
Модель сворачивает работу раньше времени, считая, что лимит контекста близко.
Guides / Sensors
Направляющие задают курс до действия, датчики проверяют результат после.
Computational / Inferential
Проверка кодом (детерминированная) против проверки другой моделью.
Sprint contract
Договорённость генератора и оценщика о том, что значит «готово», до начала работы.
Initializer agent
Первая сессия, которая готовит среду: init.sh, список фич, файл прогресса, первый коммит.
Doom loop
Агент ходит по кругу, делая мелкие вариации одного неработающего подхода.
Ralph loop
Приём сообщества: хук или скрипт снова и снова перезапускает агента с той же задачей до завершения.
Garbage collection
Регулярные фоновые задачи агентов, которые ищут дрейф от принципов и открывают мелкие PR.
Harnessability
Насколько кодовую базу легко обвязать: строгие типы, границы модулей, фреймворки.
HaaS
Harness-as-a-Service: строить поверх готового рантайма агента (Claude Agent SDK, Codex SDK), а не поверх голого API.
Brain / Hands / Session
Разделение Managed Agents: цикл с моделью, среды исполнения, журнал событий.
Blast radius · радиус поражения
Сколько вреда может причинить агент при ошибке. Уменьшается песочницей и правами.
Progressive disclosure · постепенное раскрытие
Агент стартует с короткой карты и сам идёт за деталями туда, куда она указывает.
Exec plan · план выполнения
Версионируемый план сложной работы с журналом прогресса и решений, лежит в exec-plans/.
Doc-gardening
Периодический агент, который находит устаревшие документы и открывает PR с исправлением.
llms.txt
Справочник по библиотеке или системе в формате, удобном для модели. У OpenAI лежат в docs/references/.
